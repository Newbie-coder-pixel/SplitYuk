## Commands

Flutter app (run from `app/`):
- `flutter analyze` — must be clean before considering any change done.
- `flutter test` — unit tests (`test/logic`, `test/models`, `test/state`) plus widget/screen smoke tests (`test/widget_test.dart`, `test/screens_smoke_test.dart`). Run a single file with `flutter test test/logic/split_calculator_test.dart`, or a single test with `--plain-name "some test name"`.
- `flutter run -d chrome` / `-d macos` — only screens that don't touch camera/contacts/OCR plugins (those are Android/iOS-only) will function on these targets; useful for a quick non-hardware smoke check, not full verification.
- No Android emulator or iOS simulator is set up in *this development environment* (this Mac's Xcode/Android SDK), but the app itself has been run on a real iPhone 14 by the user via an unsigned CI-built IPA + Sideloadly — see the iOS build/sideload workflow below. Real on-device bugs found and fixed that way: missing `NSCameraUsageDescription`/`NSPhotoLibraryUsageDescription`/`NSContactsUsageDescription` in `ios/Runner/Info.plist` (iOS silently kills the app on first camera/contacts use without these — always check for this class of bug first if a permission-gated feature crashes instantly on iOS with no dialog shown), and a `Column` without `mainAxisSize: MainAxisSize.min` inside a `Scaffold.bottomNavigationBar` collapsing the body to zero height (Scaffold gives the bottom bar slot unbounded height for sizing, so a default-`MainAxisSize.max` Column there tries to fill it) — watch for both patterns elsewhere.
- **iOS build/sideload, without Xcode on this machine:** `.github/workflows/build-ios-unsigned.yml` builds an unsigned `.ipa` on a GitHub-hosted macOS runner (`flutter build ios --release --no-codesign`, passing `--dart-define=SPLITYUK_RELAY_URL=https://splityuk-relay.vercel.app`) and uploads it as a workflow artifact; trigger via the Actions tab ("Run workflow") or by pushing a change under `app/**`. The user signs/installs it locally with [Sideloadly](https://sideloadly.io) using a free Apple ID (re-sign every 7 days — Apple's free-signing expiry, not a bug). `ios/Runner.xcodeproj`'s `IPHONEOS_DEPLOYMENT_TARGET` is `16.0` — Flutter 3.47.x requires iOS 15+ and `google_mlkit_commons` specifically requires 15.5+; don't lower this without checking both.

Backend relay (run from `server/`):
- `npm install`
- `npm run typecheck` (`tsc --noEmit`) — must be clean.
- `vercel dev` / `vercel deploy` — see `.env.example` for the full env var list (Fonnte, Resend, Upstash, Gemini). The relay is deployed; missing keys degrade individual endpoints gracefully rather than breaking the whole relay.
- **Deploys are automatic:** `.github/workflows/deploy-relay.yml` runs `npm run typecheck` then `vercel deploy --prod` on *every* push to `main` (needs the `VERCEL_TOKEN`/`VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` repo secrets). So merging a `server/**` change to `main` ships it to the live relay that the sideloaded iOS build already points at — don't push a half-finished relay change to `main` expecting a separate manual deploy step, and a red typecheck blocks the deploy rather than shipping broken code.
- Vercel functions here use the **named-export-per-HTTP-method** signature (`export async function POST(req: Request): Promise<Response>`), not a generic `export default`. A default export silently gets treated as a legacy Node handler, which manifests as `FUNCTION_INVOCATION_TIMEOUT` — if a new endpoint hangs/times out instead of erroring, check the export style first, not the endpoint logic. Also requires `"type": "module"` in `server/package.json` (the build otherwise emits ESM `import` syntax into a `.js` file Node then tries to load as CommonJS, failing with `SyntaxError: Cannot use import statement outside a module`).

## What this product is

SplitYuk is a mobile app (Flutter, Android & iOS) for splitting a bill among a group via receipt-scan OCR or manual input, then notifying each member of their amount owed over WhatsApp (Fonnte) and/or email. It does not process payments — it only tells people what they owe and lets them coordinate payment themselves outside the app.

Read the full PRD before making product or architecture decisions — it is the single source of truth. The sections below summarize the constraints that most affect how code should be structured; they are not a substitute for reading §1–17 directly.

## The defining constraint: no personal data is ever stored

This shapes almost every architectural decision in the PRD (§3) and must not be casually broken by "helpful" additions like caching, logging, or draft-recovery:

- **Never stored anywhere (server or on-device, beyond the active session):** bill contents, receipt photos, item lists, contact data, member phone numbers/emails, payment status history.
- **Never collected at all, even transiently:** payment destination info (bank account, e-wallet, QRIS). This was deliberately removed from scope (§6, §9.6) rather than "secured" — don't reintroduce it, including via seemingly harmless features like a QRIS image attachment (explicitly rejected in §10).
- **The only server-side state that may persist across sessions:** (a) a per-installation rate-limit counter, and (b) fully anonymized aggregate delivery-success counters. Neither may ever be linkable to a bill, phone number, name, or person (§12).
- **Transient processing ≠ storage:** the backend relay legitimately sees phone numbers/emails/amounts/images for the duration of a single request (notification send, or receipt read — see the AI OCR note below), but must not log, cache, or persist any of it — scrub these fields from platform access logs too.
- **Consequence:** there is no draft recovery. If the app is closed/killed mid-flow, the bill is gone (§11.7, FR-8.3).

Any change that adds a database table, file write, or cache entry for bill/contact/payment data is a violation of the core design principle, not just a code-quality nit — flag it explicitly rather than implementing it quietly.

**Deviation from the PRD, made deliberately with the user's explicit sign-off (2026-09-04):** PRD §9.2/§12 originally specified OCR running fully on-device (Google ML Kit) with the receipt photo never leaving the device except as a notification attachment. After real-world testing showed the on-device OCR + regex parser badly misreading a real multi-line retail receipt (see `ReceiptParser`'s doc comment and `test/logic/receipt_parser_test.dart`'s end-to-end test), the user chose to send the receipt photo to Google Gemini (via the relay's `/api/parse-receipt`, key held server-side) for direct reading instead — deliberately trading the "photo never leaves the device at scan time" property for materially better accuracy, since no amount of downstream logic can recover text the on-device OCR already misread. On-device ML Kit OCR + `ReceiptParser`/`ReceiptValidator` are kept as an automatic fallback in `ScanReceiptScreen` for when the relay is unreachable/unconfigured, not removed. If you touch this area, keep §3's principle intact for everything *except* this one explicitly-approved exception — don't let it quietly widen to send anything else off-device.

## Architecture (per PRD §13–14)

- **Mobile app — Flutter.** All bill/member/split state lives only in-memory for the session (`Bill`, `BillItem`, `Member` — see §14 for exact fields). Receipt reading is AI-first (Gemini, via the relay — see the deviation note above), falling back to on-device Google ML Kit OCR when the relay is unavailable; any temp file the OS creates for camera/gallery access must be deleted immediately after use (open item, §17).
- **Backend — stateless serverless functions** (Vercel Functions, Node/TypeScript). Its jobs: hold the Fonnte/email/Gemini API keys server-side, relay one notification or one receipt-read request at a time, and increment the anonymized counters. It must not model bill/user data — no relational database is used or needed.
- **Rate-limit/metrics store — a lightweight KV store (e.g. Upstash Redis),** not Postgres — deliberately sized to hold nothing but anonymized counters, keyed by a random per-installation token (not a phone number or any identifier).
- **Notifications:** WhatsApp via Fonnte (unofficial gateway — see risk note below), email via Resend/SendGrid as fallback. No hosted links are ever generated for bill detail; instead the receipt photo (scan flow) or an on-device-rendered summary image (manual flow, via `RepaintBoundary` or equivalent) is attached directly to the message.
- **Split calculation:** supports itemized assignment (including splitting one item across several members) and quick modes (equal / percentage / custom amount). Tax/service/discount distribute proportionally to each member's item subtotal by default, with an "equal split for extras" option. Rounding remainder defaults to the bill creator. All member shares must sum to the bill total before the flow can proceed (FR-5.4).

## App code structure (`app/lib/`)

- `models/` — `Bill`, `BillItem`, `Member`, `SplitMode`/`DiscountConfig`. Plain mutable Dart classes; `Bill`'s money fields (`subtotal`, `taxAmount`, `total`, …) are **derived getters**, not cached fields, so they can never drift out of sync with an edit.
- `logic/` — `SplitCalculator` (the money math), `SplitValidator` (gates whether a split can be calculated/sent), `SplitResult`/`MemberShare`, `ReceiptParser` (OCR-text-to-line-items heuristic) and `ReceiptValidator` (rejects photos with no price/receipt-keyword signal — a heuristic filter on OCR text, not an image classifier, so it catches the obvious non-receipt and nothing more), `OcrLayout` (rebuilds visual reading order from OCR line bounding boxes). This is the most correctness-critical code in the app — see the invariant below before touching it.
- `state/session_controller.dart` — the single `ChangeNotifier` holding the entire in-memory session (the current `Bill` + member roster). There is no other state management layer and no persistence underneath it; `resetSession()`/`closeSession()` are the only ways state is cleared, matching PRD §3.
- `services/` — thin wrappers: `AiReceiptService` (calls the relay's `/api/parse-receipt`, Gemini reads the photo directly — the primary scan path), `OcrService` (ML Kit, mobile-only, fallback when the relay is unreachable), `ContactsService` (flutter_contacts, mobile-only), `NotificationService` (calls the relay's `/api/notify`), `ImageRenderService` (captures a `RepaintBoundary` to PNG for the manual-entry summary image). `AiReceiptService`/`NotificationService` both read `--dart-define=SPLITYUK_RELAY_URL=...` and report `isConfigured: false` gracefully if it's unset.
- `screens/` — one folder per step of the PRD §8 flow (`intro`, `create`, `scan`, `members`, `assignment`, `split`, `send`, `status`), navigated via plain `Navigator.push`/`MaterialPageRoute` — no named-route table.
- `core/` — `theme/` (implements design.md's tokens: `AppColors`, `AppTypography`, `AppSpacing`/`AppRadius`), `widgets/` (the reusable receipt-styled components: `ReceiptCard`, `StampBadge`, `DashedLine`, `AmountRow`, `MemberAvatar`, `SegmentedTabs`, button variants), `utils/` (`CurrencyFormatter`, `IdGenerator`, `InstallationId`, `TempFileCleaner`).

**The `SplitCalculator` invariant** (see its doc comment and `test/logic/split_calculator_test.dart`): for every split mode, the sum of every member's final integer share always equals `Bill.total` exactly — no fractional Rupiah, nothing lost or invented to rounding. Any rounding remainder is charged entirely to whichever member is `isCreator`, as one final adjustment, never spread across everyone. All intermediate math stays `double` and is rounded exactly once, at the end, per member. If you change this file, the reconciliation tests must still pass.

**Known simplifications versus the PRD**, made deliberately for lower risk rather than by accident:
- Receipt capture uses `image_picker` (camera source), not a custom live-viewfinder UI — covers FR-2.1 without the platform-specific risk surface of the raw `camera` plugin.
- `NotificationService.isConfigured`/`AiReceiptService.isConfigured` are false whenever the app isn't built with `--dart-define=SPLITYUK_RELAY_URL=...` (e.g. local `flutter run` without that flag) — both screens say so plainly rather than pretending success. The GitHub Actions iOS build workflow does pass this flag.
- The per-installation rate-limit token (`InstallationId`) is the one thing persisted on-device across sessions (via `shared_preferences`) — this is the PRD §12/§3 narrow exception, not a violation of it.
- **The fallback OCR path never reads ML Kit's `RecognizedText.text`, and must not go back to it.** That property joins ML Kit's *blocks* in block order, and on a receipt ML Kit routinely emits the description/goods-code column as one block and the qty/amount column as another — so `.text` can list every product name first and every price afterwards, leaving prices detached from their items. `OcrService` therefore flattens every block's lines, and `OcrLayout.toReadingOrder` regroups them into the rows they physically occupy (vertical-overlap grouping chained against each row's previous fragment, so a hand-held photo's skew doesn't split a row), left-to-right within a row.
- **`ReceiptParser` deliberately assumes nothing about lines-per-item.** OCR does not reproduce printed line breaks reliably (it merges an amount row with the next product's name, or splits one row across three), so the parser reads the whole receipt as a token stream cut into alternating text runs and numeric runs, pairing each numeric run with the text run before it; within a numeric run the *last* plausible amount is the line total and everything before it is a goods code and/or quantity. A "price" is 100–999,999,999 with at most 9 digits, which is what keeps a 17-digit barcode and a qty of `1` from being read as money; numbers *after* the line amount are handed back to the next run, since they're the next item's leading quantity (`2 Nasi Goreng 40.000` / `1 Es Teh 8.000`). Only a text run's **last line** becomes the item name, so stacked header/address lines don't get glued onto the first item. It also normalizes what shops decorate prices with — `Rp25.000`, `Rp 25.000`, `25.000,-`, dotted leaders, `1.` ordinals — and multiplies `qty x unit` when a receipt prints no line-total column. `test/logic/receipt_parser_test.dart` pins ~17 distinct real-world POS layouts (warung, cafe, minimarket, retail-barcode, English invoice) plus the OCR line-break shapes; **that group is the whole point of the parser — treat a format it can't read as a bug and add a test, and don't "simplify" it back into a per-line regex.** Two limits are deliberate: amounts are read as Rupiah, so a `.`/`,` before a final 3-digit group is always a thousands separator (a western `4.50` is not understood, because reading it as 4.5 would mean misreading the far commoner `3.000` as 3), and a description OCR wrapped across two lines keeps only its second line.
- `/api/notify` and `/api/parse-receipt` rate-limit independently per action (`checkRateLimit(token, action, ...)` in `lib/rateLimiter.ts`) so one doesn't cannibalize the other's quota — this matters especially for `/api/parse-receipt`, which shares one Gemini free-tier daily allowance across every installation using this relay.

## Known unresolved risks to keep in mind

- **Single shared Fonnte number (§15, §17):** if every install sends WhatsApp messages through one Fonnte-linked number, that number will almost certainly get banned at scale and looks suspicious to recipients. This is flagged as the most serious open risk in the document and needs a dedicated design pass (per-installation device linking, or migrating to the official WhatsApp Cloud API) — don't treat the current Fonnte integration as a finished, scalable design.
- Third-party services (Fonnte, the email provider, Google/Gemini) may retain their own delivery/processing logs outside our control — this must stay disclosed in the app's privacy notice, not hidden.
- **`server/lib/gemini.ts` has now been exercised against the live API (2026-09-04), and the endpoint it was written against is correct** — `POST https://generativelanguage.googleapis.com/v1beta/interactions`, `x-goog-api-key` header, `input` array of `{type, text|data+mime_type}`, `response_format` for structured JSON. What the first three real calls showed is that *the call is unreliable, not wrong*: one returned HTTP 500 "this model is currently experiencing high demand", one stalled with no response at all, and one returned a perfectly good HTTP 200 whose payload shape the original single-field extractor rejected. All three are now handled — per-attempt `AbortSignal.timeout`, retries with backoff across a model chain, and a structure-agnostic `extractResult` that walks the whole response for anything that *is* a valid receipt result instead of trusting one documented field name. **Don't re-narrow that extractor to a single field path**; the shape has already proven to move.
- **Model choice is resolved at runtime, not pinned.** `resolveModels()` uses `GEMINI_MODEL` if set (a single id or a comma-separated preference list), otherwise asks `GET /v1beta/models` what exists right now and prefers the newest vision-capable `flash` models, filtering out embedding/tts/image/preview variants. `FALLBACK_MODEL` in the file is only reached when that listing itself fails. If parsing starts failing for everyone, check Vercel's function logs first (`vercel logs <url>` from `server/`) — an "Unrecognised Gemini response shape" warning there prints key names and value *types* only, deliberately never any receipt content (§12).
